# Asset Package Operations

## Plan, confirm, execute

The desktop UI requests a Core operation plan before moving, renaming, or deleting an asset package. The confirmation dialog lists the source and destination paths, with expandable lists of all indexed assets affected and package dependencies, plus any safety checks that block execution. Core rebuilds the plan immediately before executing it and rejects a plan whose paths, indexed assets, dependencies, package entries, or warnings changed after confirmation.

Move and rename operate on the indexed asset directory as one package. The same asset IDs and metadata remain in SQLite; Core updates primary-source, package, dependency, card paths and the owning root. A moved package must land inside a registered root of the same asset type. Rename accepts one package at a time. Batch selection supports move and recycle.

`delete_model` is a separate PMX-only model deletion plan; the older package-level `recycle` action keeps its existing behavior. Core counts `.pmx` files directly on disk in each selected PMX's parent folder, regardless of indexing or parse status, and searches the package for other supported MMD primary files. If a folder has exactly one direct PMX and is not a registered Root/container, has no other supported MMD primary file, unrelated indexed assets, nested Root, or reparse point, the plan sends the whole folder to the Windows Recycle Bin. Subdirectories that only contain package files such as textures and notes are included in the full-folder snapshot and may be recycled with the model. Otherwise the whole batch is fixed to PMX-only mode. A PMX-only plan sends only the selected PMX files; the containing directory, other models, textures, notes, and card sidecars stay in place. If the same PMX is indexed through overlapping Roots, every matching visible model row is included in the index update.

The confirmation dialog shows the chosen deletion mode, all target paths, direct PMX counts and names for each parent folder, the affected index rows, and—when deleting a folder—the complete folder entry snapshot. PMX-only plans list paths that remain. Failure to enumerate the selected PMX's direct parent blocks plan creation; if Core cannot fully verify a whole-folder scope, it falls back to PMX-only. A stale primary/dependency snapshot, changed PMX set, reverse dependency, active job, or unresolved operation blocks execution. Core rebuilds the plan after confirmation and compares these snapshots before calling the Recycle Bin API. PMX-only deletion removes only matching PMX asset IDs from SQLite and deliberately leaves `.MMDRCV` files untouched, so a sidecar may remain orphaned by design.

## Safety checks

Core blocks operations when the package is the asset root itself, contains another registered root, includes a symlink/reparse point, has an external, missing, or unknown parsed dependency, contains a retired X record, is referenced by another indexed asset according to parsed metadata or `asset_files`, has an active thumbnail job, or has an unresolved operation-journal entry. A missing standard PMD shared Toon file (`toon01.bmp` through `toon10.bmp`) is allowed because the renderer provides those built-in textures; custom or existing external Toon files remain dependencies. Missing dependency metadata for PMX/PMD assets is treated as unknown and requires a rescan. Move targets must be empty and inside a matching registered root. This first implementation also blocks loose assets directly in an asset-root folder; put those assets in their own package subfolder before using file operations.

Before offering a plan, Core compares each primary file's current size and modification time with the last indexed scan version; a mismatch requires a rescan. The confirmation snapshot then captures primary files, parsed dependencies, and every package directory/file by path, size and modification time. Core compares these snapshots after rebuilding the plan at execution time, so changed, added, or removed package entries invalidate confirmation. This check does not read or hash full file contents, so same-size changes with preserved modification times are not detected.

An operation is recorded as `Started` before the filesystem action. Move and rename use the Windows Shell `IFileOperation` API, preserving Unicode paths and supporting cross-volume moves. Delete uses the Shell recycle flag and never falls back to permanent deletion. Shell progress and error dialogs are suppressed because the desktop confirmation dialog already presents the operation plan. These behaviors follow Microsoft's [`IFileOperation::SetOperationFlags`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags) documentation for `FOFX_RECYCLEONDELETE`.

After a successful filesystem operation, Core updates the index in a SQLite transaction, marks moved cards stale, refreshes relation indexes, and completes the journal entry. If a move's index update fails, Core attempts to move the package back. If rollback cannot be confirmed, or a recycle operation is interrupted, the journal records `RecoveryNeeded`. Batch failures record paths already completed, the failed/uncertain path, and paths not started; a database failure after all recycle actions records all paths already sent to the Recycle Bin. On the next desktop start, unfinished entries are marked for recovery and affected assets are blocked from further file operations. The user must inspect the recorded paths, restore or rescan as appropriate, then explicitly mark the entry resolved. The journal is a recovery aid; it does not automatically undo operations.

The operation journal stores the operation, affected asset IDs, source and destination paths, timestamps, status and result. It is available from the desktop top bar. Permanent deletion and automatic restore are not implemented.
