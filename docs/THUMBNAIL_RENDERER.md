# Thumbnail Renderer

## Current implementation

Thumbnail rendering lives in `mmdbridge-core`; it does not use a browser screenshot, an external MMD installation, PMXEditor automation, or agent-generated images.

Renderer 0.6.1 accepts PMX and PMD model files, PMX and PMD scene assets, and VMD/VPD Motion assets. X format rendering was retired in G3-04; existing X card files and database history are retained but no longer read, verified, or refreshed by Core. Motion previews use the PMX or PMD saved in Settings → Motion Preview Model. PMD previews evaluate bones, IK and vertex morphs; PMD physics is not simulated. VPD applies named local bone translations and rotations; VMD samples bone tracks and vertex, group, bone, UV, material, flip and impulse morphs at the configured preview frame (currently frame 0, falling back to the first mapped Bone/Morph keyframe when frame 0 has none). When a VMD contains camera keys, its interpolated target, rotation, distance, FOV and perspective toggle control the still preview; camera-only VMD files use the configured model with the sampled camera. Orbit position and negated Euler rotation follow the [Three.js r160 MMDLoader camera-animation reference](https://github.com/mrdoob/three.js/blob/r160/examples/jsm/loaders/MMDLoader.js#L1699-L1799). VMDs without camera keys retain standard library framing. The preview frame is saved in the MMDRCV render report. Changing the configured model marks existing Motion cards stale. Motion cache versions also include size/mtime of referenced diffuse, sphere and Toon textures, including missing-to-present transitions. `Library::render_thumbnail` renders the preview, and `Library::create_card_with_thumbnail` stores the result inside MMDRCV. Desktop card creation enqueues a Core job; CLI `cards create` / `cards refresh` use that Core path. The desktop grid fetches card previews only as they approach the viewport.

For tag-only updates, CLI `cards sync-manifest --asset-id <id>...` calls `Library::create_card(id, None)` for each asset with a current usable thumbnail and reports per-asset failures without rendering a new preview. The command exits unsuccessfully and sets `partialFailure=true` if any item fails. CLI `tags batch-add --name <tag> --asset-id <id>...` uses Core's transactional batch tag API.

The output is 1024×1024 WebP quality 50. The GPU uses 4× MSAA when both the colour and depth formats support it, with a single-sample fallback recorded as `antialiasingSamples` in the report. Model, VPD, and VMD-without-camera framing is orthographic with a 5-degree downward view. Models select the dominant visible surface and adjoining mesh components in camera space, then frame all retained vertices with an 8% margin. Grossly stretched triangles, remote disconnected fragments and effectively invisible material/vertex-alpha surfaces are omitted only from automatic character thumbnails. Body-bone weights help choose the subject; bone positions never set the crop. Long hair, skirts and wings near the subject remain included. Unreferenced vertices do not enlarge the frame. See [subject framing rules and verification](SUBJECT_FRAMING_20261006.md) for thresholds and limitations. Scenes use a fixed 90-degree perspective camera at (0, 165/8, 0) MMD units, looking toward -Z with a 5-degree downward view and +Y up; the scene viewer starts from this same position and direction. A VMD camera track replaces that framing with its sampled camera view, including perspective or orthographic projection. PMX material index groups, diffuse / ambient / specular colors, diffuse textures, Toon ramps, multiply / add / UV-space sphere maps, and BDEF1 / BDEF2 / BDEF4 / SDEF / QDEF skinning are supported. VMD previews apply vertex, group, bone, primary UV, material and flip morphs at the selected preview frame. A sampled active impulse morph runs a bounded two-step Rapier rigid-body preview and writes dynamic-body transforms back to the skeleton; this is a still-image approximation, not replay of the full VMD physics timeline. PMX vertex-color materials use the first additional UV channel as color. PMD materials use diffuse colour, ambient colour, specular highlights, diffuse textures in either position of a `diffuse*sphere` pair, sphere maps and Toon ramps. Toon index 255 disables Toon. PMD model/scene vertices use the stored rest mesh; motion previews skin that mesh and apply PMD vertex morphs through the base morph table. The renderer report, selected adapter and diagnostics are stored in the MMDRCV manifest. The report records renderer and preview-settings versions. Only a `CardValid` card with matching source fingerprint and renderer/settings versions can supply a cached WebP. WGPU is built with Vulkan and GLES backends; if neither backend exposes an adapter, the renderer returns a structured error.

The current thumbnail settings apply the VPD/VMD pose before calculating motion framing and add a restrained view-facing matcap fill to diffuse shading. Existing MMDRCV thumbnails need regeneration to show these changes. The separate VMD 3D viewer samples Core bone poses continuously at 30 frames per second and provides a timeline and matching camera tracks; its real-time skinning approximates SDEF/QDEF linearly and does not yet animate vertex or material Morphs.

Texture decoding currently accepts BMP, JPEG, PNG and TGA, resizing textures to the device-reported 2D limit capped at 4096 pixels on their longest edge. Each render budgets external decoded/GPU textures to 256 MiB; later textures shrink to the remaining budget or use a diagnostic fallback. Original path spellings are tried before trimmed paths with Windows separators normalized for other platforms. Failed resolutions are deduplicated within a render. Missing diffuse / sphere textures use the white fallback and record a diagnostic; a missing default Toon image uses the corresponding built-in MMD Toon PNG from Three.js MMDLoader r160, while custom Toon files are loaded directly. PMX shared Toon indices follow the standard toon01-to-toon10 mapping. Impulse preview starts from the sampled pose and applies active impulses for two fixed 1/65-second steps; it does not replay earlier VMD frames, so motion-dependent results may differ from MMD applications. Joint types and collision behavior are approximated by Rapier. VMD camera tracks are rendered at one selected still frame, without timeline playback; VMD light animation is not applied. The camera preview uses the square thumbnail aspect ratio, so framing can differ from a widescreen MMD viewport. The first additional UV channel supplies PMX vertex colours and SubTexture sphere-mode-3 coordinates; its VMD UV morphs update both uses. Additional UV channels 2–4 and edge / point / line drawing are not rendered. Retired X records cannot create new Core cards.

The built-in toon00-to-toon06 PNGs are copied from [Three.js r160 `MMDLoader.js`](https://github.com/mrdoob/three.js/blob/r160/examples/jsm/loaders/MMDLoader.js#L364-L381), © 2010–2023 Three.js Authors, under the [MIT License](https://github.com/mrdoob/three.js/blob/r160/LICENSE).

## Queue and cache

Character PMX and PMD thumbnails prioritize the dominant visible mesh cluster with a margin, without choosing skeleton bounds. Automatic VPD/VMD thumbnails use the same selection after posing; scenes and valid VMD camera tracks retain their authored camera and complete triangle lists. Scene PMX and PMD thumbnails use a 90° perspective camera at world center, 165 cm above the floor (20.625 MMD units), looking toward -Z; their own scene preview version lets model and motion cards retain their cache. Cutout textures use alpha masking so hair and clothing edges write depth, while fractional transparency still uses blending.

The Core persists thumbnail jobs in SQLite with `Pending`, `Parsing`, `Rendering`, `Encoding`, `Completed`, `Failed` and `Cancelled` states. It supports priority, batch enqueue, cancellation and retry. A 24-thread Core pool selects the highest-priority pending tasks, while independent Parse, Render and Encode gates enforce stage caps. Settings → 缩略图阶段并发上限 supports Auto, 1, 2, 4, 8 and custom values from 1 to 8; changes apply immediately. Auto uses up to 8 CPU workers for Parse and Encode, and one Render worker to limit GPU contention. Pending tasks are persisted in SQLite and the in-process priority queue can hold a large library batch. Pending work resumes when the desktop Library opens; a conditional database claim prevents two Core clients from processing the same queued job. Cancellation is checked while waiting for a stage slot, between stages and between material texture loads; an active GPU draw cannot be interrupted mid-command. The desktop job bar polls progress and exposes cancel / retry actions. CLI `thumbnail enqueue` and `thumbnail batch` wait for terminal job results before exiting, so their background work is not lost with the CLI process.

Cache eligibility uses the scanned primary-source fingerprint plus the renderer and preview-settings versions stored in the manifest. The scanner also checks indexed package dependencies by size and modified time; if one changes, its card remains `CardStale` through verification and must be rendered again before it can supply a cached WebP. Schema v13 records each verified MMDRCV's file size/mtime and current manifest/renderer revisions. Routine scans use those stamps to skip reading unchanged card archives and their previews; missing, stale, changed, or not-yet-cached cards still receive deep verification, and the explicit “校验” action always performs a deep check. The first scan after upgrading fills the v13 cache fields. Unsupported source formats fail thumbnail jobs with a structured error; a user can still create a metadata-only MMDRCV card from the desktop action.

Pure-Camera VMDs are auxiliary and are excluded from normal card discovery, direct card access, and thumbnail enqueue/retry. The schema v12 migration cancels their unfinished thumbnail jobs but leaves existing card files and historical tags/favorites in place; pairing and motion preview continue to read their source VMDs through the relation index.

## Candidate investigation

The external MDanceIO 0.1.2 offscreen renderer compiled on Windows, but it did not load either of the two real PMX samples used for the runtime check: `REM式プロセカ風初音ミクVS.pmx` failed with `ModelMorphCorrupted`, and `EMT.pmx` failed with `BufferEnd`. Neither run produced an image. This does not establish that the source files are malformed.

The existing `mmd-anim-format` parser and `mmd-anim-runtime` both parsed and evaluated those same files successfully with zero parser diagnostics (72,354 / 21,927 vertices and 802 / 389 evaluated bones), so Core uses that parser/runtime path instead of adding a second PMX parser.

## 2026-09-30 Library update

Renderer 0.5.1 and model/scene preview settings v7/v3 mark old cached previews as `CardStale` when the library opens. Settings can enqueue regeneration of all visible assets through the existing cancellable/retryable thumbnail queue. Missing/failed sources and motions without a configured preview model are skipped. Per-asset regeneration invalidates its cached preview, enqueues only that asset, and updates the corresponding UI card when complete. Texture decoding detects the file format from content, with a trimmed extension fallback for TGA, preserving the existing decode limits.

A read-only Core probe of the reported Miki PMX produced a 1024x1024 full-body preview on RTX 4090, with 38,737 vertices, 56,595 triangles, and 41 diffuse textures loaded; no texture-load failure remained in its report. UI startup time and interactive layout/scene navigation were not measured or tested.

## 2026-10-01 Preview rendering and loading

Renderer 0.5.2 and model/scene settings v8/v4 add broad analytic Matcap light/shadow lobes and a soft rim while retaining diffuse, Toon and Sphere Map materials. Older thumbnails become stale through the existing version checks and can be regenerated from Settings. Completed 1024x1024 GPU colour/depth targets and unmapped readback buffers are pooled; each concurrent render uses its own resources, and failed readbacks never enter the pool. The existing parse/render/encode concurrency limits remain in effect.

Core caches only model texture-reference lists (up to four models, each at most 4,096 references and 1 MiB of path text), validated by source size and modification time. Geometry loading seeds the cache, avoiding a full PMX/PMD parse for every texture request. Missing and unreferenced textures retain their existing validation. No decoded image or full parsed model is kept in this cache. PNG encoding already uses the image library's fast default and has not been changed.

All three viewers have larger viewport-bounded windows. Model and motion orbit zoom speed is 0.45 (previously 0.075). Scene wheel input adjusts vertical FOV between 20° and 110°, retaining the 90° default and existing WASD/QE movement. Texture loading deduplicates material references and uses two workers, checks viewer disposal, and disposes late textures. Model vertex colours are recomputed only when their colouring inputs change; wireframe geometry is created on demand. Motion loading skips the weight-analysis pass used only by the model inspector.

Transparent PMX material groups sort by their individual centres instead of sharing the mesh-origin depth. Blended materials disable depth writes and discard effectively invisible fragments; cutout materials keep depth writes and use MSAA alpha-to-coverage. Model near planes are tightened, scenes use logarithmic depth, and wireframe overlays use polygon offset. These reuse [Three.js material controls](https://threejs.org/docs/pages/Material.html) and the existing r160 renderer. Intersecting transparent triangles and exactly coplanar source surfaces can still show artefacts; motion sorting uses rest-pose group centres, not per-frame triangle sorting.

Validation: TypeScript/Vite and portable Tauri Release builds passed. Isolated headless Edge checked the three viewers at 1040x680 with the packaged CSP, no geometry/CSP/JavaScript errors, and measured scene-wheel FOV changing from 90° to 75.17°. Targeted helper checks covered texture deduplication, a concurrency cap of two, cancellation, alpha/depth policies and camera-dependent transparent-group ordering. A current-source Core probe read the original Miki PMX without modifying it, verified reference rejection and cache invalidation using a temporary copy, loaded all 41 diffuse textures, and generated matching 1024x1024 WebP outputs twice. Cold/warm render calls took 666/193 ms on RTX 4090; the first includes GPU initialization, so this is not an old/new performance comparison. Real desktop interaction and complex transparent/coplanar assets remain unverified. Probe source and outputs are under `target/viewer-efficiency-probe.rs` and `target/viewer-efficiency-20261001/`; headless evidence is under `target/ui-layout-audit/`.

## 2026-10-06 Loading and compatibility update

Core now uses one bounded model-read/preflight path for scans, model viewers, thumbnails and runtime import. Source reads are capped at 512 MiB even if a file grows while reading. PMX/PMD section counts, record sizes, material coverage and triangle index bounds are checked before allocation or GPU submission. PMD models are selectable from Library and the direct-open dialog, with real BDEF2 and bone payloads in the existing MMDV v3 viewer format.

The motion-model setting validates the runtime before writing the setting or invalidating cards. A cyclic/unusable PMX skeleton may still receive a static rest-mesh thumbnail with `RestPoseFallback` diagnostics; it is rejected as a motion preview rig. Failed GPU initialization is not permanently cached, and readback waits have a finite timeout. These safeguards do not establish complete format or hardware compatibility.

The generated-fixture matrix, current build evidence, screenshot provenance and remaining compatibility limits are recorded in [MODEL_COMPATIBILITY_20261006.md](MODEL_COMPATIBILITY_20261006.md). Earlier real-model smoke results above belong to their stated historical builds and have not been rerun in this environment.
