# Goal 2 · B｜扫描、队列与恢复

## 本册目标与完成条件

- 目标：先给出跨进程 owner/lease、恢复和迁移的可审查设计，再实施获准的中大型机制；贴图事件等局部缺陷可先单独修复。
- 批次完成条件：扫描期间变更不会丢失；活跃进程不会被误接管；取消在资源释放前不会显示完成；迁移可中途失败并回滚。
- 证据级别沿用原排查文档；静态确认不等于运行验证。每项先核对当前源码是否已变化，若已修复，记录证据后跳过重复实现。
- 本册原有条目文本完整保留，下面的“执行契约”补充可交付边界；与用户最新要求或根目录 `AGENTS.md` 冲突时以后者为准。

## 任务与执行契约

### G2-02：递归扫描、监视与队列控制

**证据**：`scanner.rs::scan/dependencies_unchanged`、`scan_queue.rs::enqueue/continue_paused/worker_loop`、`file_watcher.rs::event_relevant/is_indexable_change/watch_loop`。

**问题**：

- [确认] 监视过滤仅接收目录及 PMX/PMD/VMD/VPD/X，PNG/JPG/TGA/BMP/SPH/SPA 等依赖变化不会触发扫描。扫描器能检查部分依赖变化，但前提是扫描已经启动。
- [确认] 活跃扫描期间再次 `enqueue` 不更新状态；watcher 却先移除 `pending_roots`。若对应文件已处理过，本轮后续又没有新事件，变化可能没有下一轮补扫。
- [确认] 遍历遇到一条 WalkDir 错误即终止 Root；逐文件读取 metadata 失败则直接跳过，报告缺少该文件的清晰错误。
- [确认] Discovering 按 1024 个条目、Indexing 按 32 个文件检查进度与中断；单个大文件解析和关系/重复分析期间可能长时间无法响应暂停。
- [设计] Discovering 固定进度 2%，不是已知总量百分比。“继续”会重新遍历，当前队列说明已写明，应该保留这份诚实说明。

**修改方案**：

1. 优先基于 Core 已登记依赖路径接收事件，并覆盖缺失依赖补回；目录删除和重命名不能仅靠事件后 `is_dir()` 判断。忽略自身 MMDRCV 临时发布事件，外部卡片变化可单独校验。
2. 持久化 Root 的 dirty generation 或 `rescan_requested`；活跃任务结束后至多追加一次增量补扫，暂停/禁用时保留待处理标记，避免事件风暴。
3. 目录不可访问记录为扫描警告并继续其他子树；未完整访问的子树禁止被批量判定 MissingSource。Root 整体离线和“扫描完成但某源文件不存在”分开。
4. 进度检查采用“文件边界＋时间间隔”，展示当前阶段、当前路径、已发现/已处理/失败数。无法准确估计总量时使用不定进度，不显示虚假的精确 ETA。
5. 缩小 Derived 阶段工作范围：先重建受影响 Root/类型的候选，再优化到资产集合；增加阶段中断点，不立即重写整个调度器。

**范围/验收**：S/M。最小用例为扫描过程中改动一个已扫描文件，以及仅替换一个贴图；期望自动补扫、对应资产变旧，其余资产不重绘。权限错误用临时目录模拟，不扫描全库做回归。

#### G2-02 执行契约

- 事件处理记录 source/依赖路径与目录变化；活跃扫描期间收到新事件时先持久标记，再在最终状态提交后安排一次补扫。
- 不可访问子树与整个 Root 离线应区分；未完整遍历区域不得被推断为 MissingSource，且应保留可重试诊断。
- 暂停/取消在阶段边界生效，界面明确当前文件可能需要完成后才能停；无法估算总量时只展示计数和阶段。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-07：缩略图/资源卡任务队列与并发

**证据**：`jobs.rs::start_worker/enqueue_thumbnail/retry_job/cancel_job`、`thumbnail_concurrency.rs`、`database.rs::list_jobs/queue_pending_cards`、`App.tsx` 任务面板。

**现状**：SQLite 持久任务、条件认领、24 个工作线程、Parse/Render/Encode 阶段限制、优先级、取消和重试已存在；设置支持 Auto 和 1～8 的自定义值。

**问题与改法**：

1. [确认] 启动恢复只把更新时间早于十分钟的运行任务重置 Pending，而且没有对应的持续恢复循环。崩溃后迅速重启的任务可能长期停在运行态。改为基于 owner/session 与存活信息判断遗留任务，显示“上次运行中断，可继续”。
2. [风险] enqueue 先查询再插入，retry 复用旧任务；并发客户端可能为同一资产生成多个活跃 job。用事务和活跃任务唯一约束处理，不仅依赖内存队列去重。
3. [确认] cancel 立即写 Cancelled，但实际 GPU 或文件发布可能尚未退出。增加 Cancelling 到终态的握手；执行中的资源释放前，文件操作仍将其视为占用。不能让用户看到“已取消”后立刻允许移动仍被读取的包。
4. [设计] 任务列表只展示最近/返回列表中的 12 项且名称统一为“缩略图”，缺少资产名、批次、范围。返回资产名、路径、batchId、阶段、失败原因和可操作项，提供“进行中/失败/已完成”。
5. [缺口] UI 没有任务提优先级、批量取消/重试、完整队列分页。复用现有 priority；改优先级时同步持久队列与内存排序。
6. [风险] 固定 24 工作者可在阶段间积压多份已解析模型；阶段并发控制不等于内存上限。先统计驻留输入量，再增加有限 in-flight 容量或字节预算，不直接增加线程数。
7. [确认] 批量入队逐项执行，遇错可能已有部分任务排入。返回 accepted/skipped/failed 明细，支持恢复入队；不要把部分成功包装成全部失败。

**范围/验收**：UI S/M，任务所有权 M/L，需先确定迁移方案。最小验证是一个长任务中断后快速重启、两个客户端同时提交同资产，以及取消后立即请求操作计划；不跑整库渲染。

#### G2-07 执行契约

- 先画出 Pending→Running→Cancelling→Cancelled/Completed/Failed 与重启恢复转移；持久表是状态真相，内存队列只是调度缓存。
- 活跃任务去重需数据库原子约束；批量入队逐项返回 accepted/skipped/failed，重复请求不得产生两个活跃任务。
- 取消完成以 worker 已退出、文件句柄/发布已结束为准；操作计划在此之前把资产视为占用。
- 跨进程 owner、lease 和迁移属于确认门槛；先交数据结构、兼容方案、失效 owner 判定与回退，再改表。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-20：操作日志、异常恢复与多客户端

**证据**：`operations.rs::execute/mark_interrupted/resolve_journal`、`database.rs::asset_operation_guard/resume_thumbnail_jobs`、CLI `Cards Generate`。

**问题**：

- [确认] 文件操作与扫描互斥使用同一 Library 的内存 Mutex，不能覆盖不同进程各自打开同一数据库。
- [确认] `resume_thumbnail_jobs` 顺带调用 `mark_interrupted`，将所有 Started 操作标为 RecoveryNeeded；CLI 生成卡也会调用它。
- [风险] 桌面正在操作文件时另一个进程恢复任务，可能把仍在运行的操作误标为中断。现有任务条件认领保护的是具体 job，不解决全部进程间互斥。
- [确认] “标记已处理”只更新日志状态，依赖用户自行确认，没有结构化检查结果；部分批量文件操作完成后失败也需要逐项恢复记录。

**修改方案**：

1. 将恢复流程从缩略图启动函数拆开，建立与数据库路径绑定的写操作 owner/lease；文件变更、扫描、卡发布按实际冲突范围协调。新进程不得无条件接管活跃操作。
2. 日志记录每个包的 Pending/FilesystemDone/IndexDone/Failed 等阶段及实际完成项，仍复用现有日志表/JSON；暂停重启后按记录生成恢复建议。
3. 恢复页提供路径存在性、索引归属、相关 Root 重扫结果的只读检查，再允许“确认已处理”。不要将按钮包装成自动撤销。
4. 若加入自动 Undo，需要单独评估目标冲突、跨卷与回收站身份，不属于本轮最小修复的默认实现。
5. 活跃操作期间前端保持明确进度并阻止重复执行；关闭确认窗口不意味着后台操作被取消。

**范围/验收**：M/L，跨进程协调方案先确认。只用临时库模拟活跃 owner 和失效 owner，证明第二客户端不会把活跃日志改为中断；实际 Shell 失败恢复后续用一个临时包验证。

#### G2-20 执行契约

- 缩略图恢复与操作日志恢复解耦；owner 存活时第二进程只读展示，不把 Started 标为中断。
- 每包记 Pending/FilesystemDone/IndexDone/Failed 与完成项；恢复先做路径和索引只读核对。
- 跨进程锁范围、lease 失效判定、崩溃后接管和迁移先提交具体方案；自动 Undo 不在当前默认范围。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-21：数据库迁移、可重建性、存储与备份

**证据**：`database.rs::open/initialize_schema/storage_info/compact_storage`、`cards.rs::CardManifest`。

**修改方案**：

1. [确认] schema 初始化无条件写 `user_version=9`，部分 ALTER 在后续独立执行。读取版本，按版本逐步迁移，每步事务，完成后再更新版本；拒绝由旧程序写入未知更高版本库。
2. [确认] SQLite 保存了 Root、设置、智能集合、未同步标签、用户关系等，MMDRCV 不能重建全部 Library 状态。文档区分“资产索引可重建”与“所有用户整理结果可恢复”。
3. [缺口] 提供 Core 备份/恢复或导出用户状态，备份时考虑 WAL 一致性；优先使用 SQLite 自带备份能力，不手抄正在写的主库文件。恢复必须先验证并保留当前库副本。
4. [确认] `storage_info` 根据当前 EXE 的默认路径统计，而不是 Library 实际打开路径。保存实际 DB 路径供查询，临时库/未来多库不能误报便携库大小。
5. [设计] 保留 512 MiB 限制前先展示真实容量与阈值告警、整理作用和受影响历史任务数量；数据库满时区分 SQLITE_FULL 与一般数据库错误。改变限额政策需单独决定。
6. [风险] `compact_storage` 持锁等待扫描再执行，前端可能只是漫长等待。先返回忙状态或排入维护任务，明确需要空闲；保留最近失败任务，不盲删用户尚未处理的错误记录。

**范围/验收**：迁移和路径 S/M，用户状态备份 M。只用一个旧版临时库升级、重开和一次回滚失败模拟；不复制或重建用户当前库做实验。

#### G2-21 执行契约

- 先读 user_version，单版本迁移在事务中完成并最后更新版本；未知高版本拒绝写入。
- 将可重建索引与不可完全由旁车恢复的 Root/用户状态分别列清；备份使用 SQLite 一致性机制。
- storage_info 使用实际打开路径；压缩忙时返回可解释状态，不在用户当前库上做迁移试验。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。
