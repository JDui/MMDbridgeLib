### G2-19：资产包 Move/Rename/Recycle 的依赖安全

**证据链（P0）**：

1. `scanner.rs::resolve_dependencies` 把依赖分成 `resolved/missing/external`，全部写到 `metadata.file_dependencies`。
2. `scanner.rs::store_candidate` 仅将 `status == "resolved"` 的依赖写入 `asset_files`。
3. `operations.rs::load_asset_dependencies` 只查 `asset_files WHERE role<>'primary'`；`prepare` 使用它做外部/缺失检查，没有补查上述 metadata。

因此，**最初扫描就缺失或在包外的依赖可能不进入操作安全检查**；现有 `docs/ASSET_OPERATIONS.md` 的阻止承诺比实现更强。此处为源码确认的漏检，不表示本次已执行移动或确认发生素材损坏。

**修改方案**：

1. 先最小修复：`prepare` 同时读取结构化解析依赖，对缺失/外部/无法确定依赖形成阻止原因；内置共享 Toon 等确实可由软件提供的依赖要按角色规则区分，不能把所有默认 Toon 一律当作缺失。
2. [风险] 检查反向依赖：其他包的资产是否引用待移动/删除包内文件。当前循环只检查选中包内资产向外依赖，不能保护其他资产向内引用的共享纹理。复用统一依赖数据建立反查，无法确定时阻止并展示受影响资产。
3. [风险] 用户可在扫描后改 PMX 引用，当前计划只对已索引依赖做检查。计划生成时先核对主文件 size/mtime 与扫描索引版本；不匹配时要求重扫。计划确认到执行前对主文件、依赖和包内全部目录/文件记录 size/mtime 与路径清单，变化则要求重新确认；不做内容哈希。
4. 保留重新生成计划、目标存在拒绝、Root 内散落文件拒绝、嵌套 Root/重解析点限制、同类型目标 Root、回收站无永久删除降级等保护。
5. [设计] 用户选择一个模型可能影响整个包。确认页以“包”作为主要单位，显示全部受影响资产，可展开所有依赖与阻止原因，不止前 12/8 项摘要。
6. 计划只读核对未通过时，给出“打开依赖列表/重新扫描/选择其他目标”等动作，不以一句“安全检查未通过”结束。

**范围/验收**：现有批准范围内 S/M。先做只生成计划的临时夹具：一个外部纹理、一个缺失纹理、一个被其他包引用的纹理，均应明确阻止；此阶段不需要实际移动或删除任何真实素材。

### G2-03：索引写入、增量缓存和资产身份

**证据**：`scanner.rs::store_candidate/find_moved_asset/scan`。已有同路径保持 ID、同 Root 唯一指纹回连、附近卡片身份恢复和歧义保护。

**问题**：

- [确认] `store_candidate` 连续写 `assets`、删除/重建 `asset_files`、更新 `metadata/cards`，没有包住这些操作的事务。错误或空间耗尽可留下部分写入。
- [确认] 外部移动的指纹回连只查同 Root；跨 Root 移动与大小写/路径规范变化不能仅依赖该逻辑。
- [确认] 普通扫描仍逐资产写 `last_seen_at`，逐张校验卡片，再全库重建关系与重复索引；“增量”不代表没有全库工作。
- [风险] 文件在读 metadata、读内容、解析和落库之间变化，可能保存不属于同一版本的大小、mtime 与解析结果。

**修改方案**：

1. 单资产落库用一个短事务，文件读取与解析在事务外完成。失败时整资产回滚，其他资产可继续；不要把整个 Root 扫描变成一笔长事务。
2. 读取前后比较 size/mtime，变化时有限重试或延后重扫；复用已读字节计算 BLAKE3，不追加无意义读盘。
3. 统一 Windows 路径 key 的规范化，显示路径保持原大小写；同 Root 回连保持现有保守策略。跨 Root 仅在源缺失、类型一致且匹配唯一时提出回连，歧义进入复核。
4. 区分“内容变更”“最后看见”“用户整理变更”，避免搜索排序或 UI 缩略图失效依赖含糊的 `updatedAt`。
5. 后续仅对变更资产重查卡与派生索引；规模优化前先记录阶段耗时，不先替换 SQLite 或引入全文搜索服务。

**范围/验收**：事务 S，身份扩展 M。只对一资产的中间写入注入一次失败，确认旧资产、主文件、依赖、卡片状态仍完整；再验证同目录改名保持 ID。

#### G2-03 执行契约

- 落库前检查读取前后文件版本；变化时有限重试或保留旧记录并排队重扫，不把混合版本标记为 Ready。

### G2-04：模型候选、状态与人工复核

**证据**：`scanner.rs::multiple_pmx_directories/scan/store_candidate`、`parser.rs::parse_asset`、`App.tsx::reviewReason/assetStatusText`。

**问题**：

- [确认] 同目录多个主模型时直接把 `parsed.status` 改成 `NeedsReview`，可能覆盖该文件原有 `ParseFailed/Unsupported`；落库又只创建一个元素的状态数组。

### G2-01：Root 添加、配置和移除

**现状与证据**：`database.rs::add_root/update_root/remove_root/initialize_schema`；`App.tsx::addRoot/addAnyRoot/updateRoot`。Root 默认递归，支持类型、启用、名称及递归属性；UI 当前 Root 行有改名、扫描、完整检查、生成卡、移除。

**问题**：

- [确认] `initialize_schema` 每次执行 `UPDATE roots SET scan_recursive=1 WHERE scan_recursive=0`，会覆盖用户经 CLI/Core 设置的非递归选项。
- [缺口] `updateRoot` 已能发送 `enabled/scanRecursive`，但当前 JSX 没有对应设置控件；Root 路径没有重定位接口。
- [设计] 通用“＋”要求输入 `model / motion / scene`，添加成功后还需要自行找扫描按钮；侧栏每行五个小图标，主动作不突出。
- [风险] 同类型嵌套 Root 未在添加时解释归属；同一路径可登记为不同类型，后续移动又会因混合类型被阻止。

**修改方案**：

1. 去掉启动时覆盖用户配置的 SQL；若它原本是历史迁移，只允许在指定旧版本升级时执行一次。增加重开数据库后配置保持的最小回归。
2. 新建“添加目录”小表单：类型三选一、路径选择、显示名、默认勾选递归、明确的“添加并扫描”。复用原 `root_add` 和 `scan_enqueue`。
3. Root 行保留一个主要扫描按钮，其余放“更多”菜单；菜单补“启用自动监视”“递归扫描”设置。区分禁用 Root 与暂停本次扫描。
4. 添加时提示已有、嵌套、重叠目录及索引影响；不自动迁移旧资产。路径重定位作为独立计划，先判断类型与身份冲突，再考虑实现。
5. 移除确认展示将移除的索引数量、收藏/标签同步状态，保留“磁盘文件不删除”说明。

**范围/验收**：S，重定位另列 M。验证一个 Root 设置持久性；后续安全 UI 验证一次添加到开始扫描的完整流程。

### G2-24：错误、日志、恢复动作与多状态呈现

**证据**：Tauri `ApiError::from`、CLI `error_code/main`、`App.tsx` 和两个 Viewer 的 `String(reason)`、`jobs.rs::update_terminal`。

**问题与改法**：

1. [确认] Tauri 返回结构化错误对象，前端大量 `String(reason)` 会把普通对象显示为 `[object Object]`。新增共用 `toUiError`，优先提取 message/code/source/assetId，再处理 Error/string。
2. [确认] Tauri error 的 asset_id/source 全为空，recoverable 一律 true；CLI 同样缺足够上下文。Core 提供统一错误编码与上下文，再由两适配器复用，避免重复映射漂移。
3. [设计] 错误放到触发位置：字段旁、预览面板、队列行、操作计划中；全局条幅只处理全局故障。提供复制诊断和有针对性的重试、选模型、重扫、查看依赖等操作。
4. [确认] watcher 部分错误只输出 stderr，窗口程序不易看见。将启动失败与持续故障保留为后台诊断状态，提示一次并允许查看，不每 1.2 秒重复刷屏。
5. [设计] 状态中文化但保留可复制技术码；区分正在停止、停止完成、失败、部分完成、人工待核对。不要把停止仍写成 100% 成功。
6. [缺口] 加本地诊断日志轮转和导出，默认只记录定位所需字段；日志与应用版本、job/root/asset/operation ID 关联。

**范围/验收**：S/M。模拟一次结构化 CardError，用户看到明确原因和下一步；一个失败 job 能追溯到资产与路径，不需要造大量错误类型测试。
