# Goal 2 · E｜批量、接口、性能与交付

## 本册目标与完成条件

- 目标：在 A～D 的相关状态和接口稳定后接通批量与 CLI，按已测瓶颈优化并发布便携版；局部独立修复可以提前。
- 批次完成条件：同一 Core 能力被 UI/CLI 共用；批次结果如实反映部分失败；性能改善有指定基线；最终 EXE 来自最终源码。
- 证据级别沿用原排查文档；静态确认不等于运行验证。每项先核对当前源码是否已变化，若已修复，记录证据后跳过重复实现。
- 本册原有条目文本完整保留，下面的“执行契约”补充可交付边界；与用户最新要求或根目录 `AGENTS.md` 冲突时以后者为准。

## 任务与执行契约

### G2-18：重复项检测与人工处理

**证据**：`duplicates.rs::rebuild/find_possible_duplicates`、`scanner.rs::list_duplicate_asset_page`、`App.tsx` 重复项详情。

**现状**：精确主文件 BLAKE3 相同、名称/大小/结构等可能重复评分、局部候选窗口控制比较量均已实现；没有自动删除。

**修改方案**：

1. [设计] 明确“主文件完全相同”与“整个资产包相同”的区别；同 PMX 不同纹理不代表可替换的相同资产。界面当前“内容完全相同”建议更精确。
2. [缺口] 增加按组比较页，展示两个预览、路径、大小、结构差异、依赖摘要；提供“保留独立/忽略此建议/去操作计划”，不提供无确认的一键清理。
3. [确认] rebuild 清空重复表并生成新 ID。人工忽略应按稳定的资产对或组键单独存，不挂在每次重建的建议 ID 上。
4. [设计] 精确和可能重复提供独立筛选。候选窗口是性能折中，文案不能宣称找到了全库所有相似资产。
5. [风险] 删除一份主文件会执行整个包操作，必须展示包内其他模型/纹理与反向依赖；复用 G2-19，不在重复模块新增文件删除逻辑。

**范围/验收**：M。两个主文件相同但纹理不同的临时包，提示正确且不默认可删；忽略建议后重扫仍忽略。

#### G2-18 执行契约

- 精确重复文案限定为主文件指纹相同；依赖不同的包不能显示成可安全替换。
- 忽略判断按稳定资产对/组键持久化，重建建议 ID 变化不影响用户决定。
- 去操作计划仅复用 G2-19 的包级安全检查；比较页展示预览、路径、依赖差异和建议依据。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-22：Core API、Tauri 与 CLI 一致性

**证据**：`lib.rs/types.rs/error.rs`、Tauri `main.rs`、CLI `main.rs` 的命令枚举与分支。

**修改方案**：

1. [缺口] JSON 响应多数为直接数组/对象，未统一 API 版本；逐步增加 `api_version` 或独立能力查询，保持现有脚本兼容，不一次改掉所有输出结构。
2. [确认] CLI assets list 只有 limit，无分页游标/Root/目录参数；超过上限无法完整遍历。复用 Core `list_asset_page` 添加分页及过滤，不让 Skill 手写数据库查询。
3. [缺口] 补 manifest-only 卡更新、批量标签、扫描队列状态/暂停/继续/取消、阶段并发设置、操作日志只读查询；按实际工作流逐个接入，文件执行命令必须承接完整计划与显式确认。
4. [确认] Tauri 多个可能耗时命令仍为同步 fn，例如资产计划/执行、卡校验、Root 移除；已有 `read_core + spawn_blocking` 可复用。文件移动需另带进度，不阻塞 IPC 主处理。
5. [确认] CLI `--json` 读取后未区分输出策略；批量生成即使有 failed 也可返回正常结果。定义 stdout 结构结果、stderr 进度、成功/部分失败/失败退出码及超时规则，避免脚本把失败当成功。
6. [设计] 显式输出数据库实际路径与版本，确保桌面和 CLI 指向同一便携库；参数错误也应能被自动化可靠识别。

**范围/验收**：S/M。一个分页查询遍历两页不漏重，一个 manifest-only 命令保留图，一个部分失败批次返回明确非全成功状态即可。

#### G2-22 执行契约

- Core 定义单一数据/错误语义，Tauri 与 CLI 仅适配；新 JSON 字段向后兼容，旧脚本输出不突然整体换壳。
- CLI 分页使用 Core 游标、实际 DB 路径；stdout 只放结果，stderr 放进度，部分失败用明确结果和退出码。
- 耗时 Tauri 命令使用已有异步/阻塞线程模式；文件执行仍要求计划与显式确认。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-23：性能与后台可响应性

**证据**：单连接 `Arc<Mutex<Connection>>`、扫描全量派生索引、`App.tsx::refresh` 多个 IPC 和轮询、VirtuosoGrid 与 CardThumbnail。

**修改方案**：

1. 已有虚拟网格与懒加载保留。不要把未测量的“卡顿”直接归咎于 React 或 SQLite，也不要先重写框架。
2. [确认] 每次 refresh 请求 roots/counts/directories/assets/jobs/summary/scans/duplicates/filters 多个端点，最终不少工作争用同一连接。把静态配置与高频状态拆开，变更时定向失效。
3. [风险] 全量关系/重复写事务与逐资产卡读取可能影响列表查询。先记录查询等待、阶段耗时、候选规模和解码驻留，再决定短事务、查询连接或派生索引增量化。
4. 任务轮询只用于活跃任务，空闲降频；防止一次轮询未结束又发下一次。可选 Core 事件推送，但必须复用同一状态机，不能两套进度真相。
5. [确认] 网格虚拟化不限制已加载 assets 数组增长。长期浏览先记录内存，必要时增加有限页缓存与回访恢复；缩略图同样使用有界版本缓存，不能无限保留 Blob。
6. 性能目标先规定场景再测：本地中等库初屏、搜索、扫描期间浏览、预览关闭后资源回收；记录机器/数据量/冷暖状态，数值目标用一次基线结果决定。

**范围/验收**：S/M；数据库读写架构拆分另评估。只测试当前改动最可能改善的一条慢路径，不每次执行 5 万资产全流程。

#### G2-23 执行契约

- 先记录目标慢路径的阶段耗时、DB 等待和 UI 请求次数，再决定增量索引或连接拆分；不凭直觉重构框架。
- 轮询仅在活跃任务期间高频且不得重叠；静态配置只在变化时刷新。
- 页缓存与 Blob 缓存若加边界，要保证回访、滚动锚点和最新缩略图版本正确。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-26：详情、卡片和批量工作的完整闭环

**证据**：`App.tsx` 的 asset-card、Inspector、bulk-actions、operation-modal。

**修改方案**：

1. [缺口] 卡片以缩略图为主的方向正确，但原 Goal 要求的 Primary Tags 尚未进入 Asset 卡片数据。Core 列表返回少量摘要标签，卡片最多显示 2～3 个，其余进详情；不要每张卡发单独 tags 请求。
2. [设计] 双击当前只打开缩略图，可增加清晰“3D/播放”悬浮按钮或用户偏好；初始保持现有双击行为，避免无说明改变熟悉的动作。
3. [确认] 批量选择只有逐项切换，缺全选/范围选择。先加“全选已加载”和 Shift 范围，并明确范围；“选择全部匹配结果”需 Core 快照方案，不在前端偷偷把 120 项当全库。
4. [缺口] 批量生成资源卡当前是 Root 级入口，没有选中资产入口。复用 `thumbnail_batch` 增加“生成缺失/同步资料/重绘”区别及预计项数，保留可取消和跳过原因。
5. [设计] 批量操作完成保留结果摘要与失败清单，允许只重试失败项；不要每次成功都自动退出选择并清空上下文。
6. 详情以固定字段分组：基本信息、预览与卡、文件与依赖、标签、关系版本、问题诊断。技术报告默认折叠，可复制，不占满卡片主视觉。

**范围/验收**：S/M。一次跨两页多选后确认范围、批量加标签和结果明细正确；选中同包多个资产时操作计划按包去重但保留受影响全部资产。

#### G2-26 执行契约

- Core 列表返回有限 Primary Tags；卡片最多展示 2～3 个，详情可读完整标签。
- 全选已加载与选择全部匹配结果严格区分；跨页选择维持稳定 ID，包级计划去重但展示全部受影响资产。
- 批量创建/同步/重绘分别计数，部分失败返回逐项结果，保留选择以便重试失败项。
- **交付记录**：列出涉及文件、旧/新行为、实际执行的最小验证、失败或未验项；仅满足本节原有验收并给出证据后标记完成。

### G2-28：维护结构、依赖复用和输入边界
